# Korean Report Writing Style Rules

한국어 보고 장표는 영어 원문을 번역한 결과물이 아니라, 한국 조직의 의사결정 언어로 다시 쓴 결과물이어야 한다.
이 문서는 HTML/PPT형 보고자료를 만들 때 제목, 소제목, 카드, 표, 라벨, 결론 박스에 적용하는 전역 문체 규칙이다.

## Reference Basis

- [국립국어원 `쉬운 공문서 쓰기 길잡이`](https://www.korean.go.kr/front/etcData/etcDataView.do?etc_seq=700&mn_id=&pageIndex=1): 공문서 작성자에게 필요한 내용을 가려 뽑아 정확한 정보 전달과 업무 투명성을 높이는 취지로 정리된 자료다.
- [공공데이터포털 `문화체육관광부 국립국어원_쉬운 공문서 쓰기 길잡이`](https://www.data.go.kr/data/15118448/fileData.do): `쉬운 공문서 쓰기 길잡이`가 쉬운 공공언어 쓰기 지침을 바탕으로 공문서 작성에 필요한 내용을 다듬은 자료임을 확인한다.
- [PUBLY `보고서의 윤곽이 살아나는, 핵심문구 작성법`](https://publy.co/content/6485): 핵심문구는 단순 요약이 아니라 결론을 먼저, 더 짧고 쉽게 쓰는 장치라는 원칙을 참고한다.
- [보고서 작성 매뉴얼 PDF](https://t1.daumcdn.net/brunch/service/user/bo5z/file/PwMJyMVW-l038IpAx-rkYjb263E.pdf?download=): 제목만 보고 전체 내용을 알 수 있도록 핵심 사항을 압축하고, `동향`, `현황`, `개요`처럼 넓은 제목을 피한다는 원칙을 참고한다.

## Core Principle

장표 제목은 “무엇이 바뀌었나”가 아니라 “그래서 무엇을 판단하거나 실행해야 하나”를 말해야 한다.

```text
제품 발표 요약 X
실무 적용 판단 O

영어식 추상어 번역 X
한국 업무어휘 재작성 O

문장형 감상 X
판단 / 기준 / 범위 / 조치 / 보류 O
```

## Message Contract

HTML을 만들기 전에 각 장표마다 아래 4개를 먼저 정한다.

| 항목 | 질문 | 산출 문구 |
|---|---|---|
| Reader | 누가 읽나 | 임원 / 팀장 / 실무자 / 개발사 |
| Decision | 무엇을 판단하나 | 적용 / 보류 / 검증 / 승인 / 공유 |
| Reason | 왜 그런가 | 근거 2~3개 |
| Action | 읽고 무엇을 하나 | 파일럿 / 정책 확인 / 체크리스트 / 개발 반영 |

이 4개가 없으면 제목을 만들지 않는다.

## Title Rules

### 1. 제목은 판단형 명사구

좋은 제목은 아래 형태 중 하나다.

- `대상 + 적용 방향`
- `범위 + 우선순위`
- `리스크 + 선행 확인`
- `비교 대상 + 전환 기준`
- `파일럿 + 검증 범위`
- `정책 이슈 + 보류 판단`

### 2. 제목 끝은 업무 명사

권장 끝말:

- `적용 방향`
- `검토 기준`
- `우선순위`
- `전환 기준`
- `운영 기준`
- `검증 범위`
- `선행 확인`
- `확대 조건`
- `보류 항목`
- `전달 포인트`

금지 또는 주의 끝말:

- `바뀜`
- `잠금`
- `대기`
- `도입`
- `혁신`
- `가능`
- `하는 것`
- `할 것`
- `이슈`
- `현황`
- `개요`

`현황`, `이슈`, `개요`는 단독 제목으로 쓰지 말고, 무엇을 판단할 현황인지 붙인다.

### 3. 영어 구조를 직역하지 않기

| 직역투 | 보고서형 |
|---|---|
| 바뀌는 건 기능이 아니라 작업 경계 | 파일 역할: 화면 검토에서 산출물 관리로 확대 |
| Figma 파일이 제작 작업대로 바뀜 | Figma 2026 적용 방향: 산출물 기준 재정의 |
| 접근 가능 기능부터 실험, 닫힌 베타는 대기 | 파일럿 우선순위: 즉시 실험과 보류 항목 분리 |
| 적용 전 잠금 | 확인 후 적용 |
| 시작 전 잠글 것: 권한·과금·공개 범위 | 확대 적용 전 권한·비용·공개범위 확인 |
| 작업 경계 변경 | 파일 역할 확대 |
| 기능 채택 | 업무 적용 |
| 닫힌 베타 | 제한 공개 항목 |
| 접근 가능 기능 | 즉시 사용 가능 항목 |

## Subtitle Rules

소제목은 제목을 반복하지 않는다.

- 제목: 판단 또는 조치
- 소제목: 판단 근거, 조건, 범위

예:

```text
제목: Figma 2026 적용 방향: 산출물 기준 재정의
소제목: Motion·Weave·Code layers는 기능 목록이 아니라 산출물 정의와 인계 기준 변경 이슈
```

## Card And Table Copy

카드와 표 셀은 `주어 + 서술어` 문장이 아니라 `업무 라벨 + 판단`으로 쓴다.

| 약한 표현 | 대체 표현 |
|---|---|
| 기능을 채택해야 한다 | 적용 후보 |
| 권한을 잠가야 한다 | 권한 확인 |
| 비용을 확인해야 한다 | 과금 기준 확인 |
| 공개 범위를 정해야 한다 | 공개범위 확정 |
| 기다려야 한다 | 보류 |
| 나중에 적용한다 | 후속 검토 |

## Korean Line And Rhythm

- `산출물 기준`, `권한·비용·공개범위`, `즉시 사용 가능 항목`, `제한 공개 항목`은 한 호흡으로 읽히는 단위다.
- 제목에서 조사는 가능하면 줄이고, 핵심 명사구를 앞에 둔다.
- 한 장표 안에서 같은 문장 구조를 반복하지 않는다.
- 영어 제품명은 남기되, 판단어는 한국어 업무어휘로 쓴다.

## QA Gate

최종 HTML 전 아래 질문에 모두 답한다.

1. 제목만 보고 독자가 판단 방향을 알 수 있는가?
2. `바뀜`, `잠금`, `대기`, `접근 가능`, `작업 경계` 같은 번역투가 남아 있지 않은가?
3. 소제목이 제목을 다시 말하지 않고 근거·조건을 보태는가?
4. 카드와 표 셀이 문장형 설명이 아니라 업무 라벨로 정리됐는가?
5. 같은 내용을 한국 회의자료에서 실제로 말할 법한가?
6. 줄바꿈이 의미 단위 기준으로 끊기는가?
7. 이미지가 장식이 아니라 판단 근거, 화면 증거, 적용 범위를 보여주는가?
